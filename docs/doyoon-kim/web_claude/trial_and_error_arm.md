# 시행착오 기록 — 로봇팔 제어 파트 (노션용)

> 웹 클로드 시각화 의뢰용. **내용만** 작성. `[이미지 N]` 은 준비된 그림이 있는 항목.
> 준비된 이미지 파일 경로는 문서 맨 끝 "이미지 목록" 참조.

---

## 이 문서의 관점

실패를 나열하는 것이 목적이 아니다. **같은 함정에 두 번 빠지지 않으려면 무엇을 봤어야 했는가**를 적는다.
그래서 각 항목은 `증상 → 처음 의심한 것 → 실제 원인 → 무엇을 봤어야 했나` 로 쓴다.

## 1. 관통하는 교훈 — "검사는 통과했는데 실제로는 안 된다"

`[이미지 1]` — 정적 검사 vs 동적 검사 개념도

세 번 같은 형태로 당했다.

| # | 확인했다고 믿은 것 | 실제로 해 보니 |
| --- | --- | --- |
| 1 | 롤백 절차 (문서에 적음) | `~/arm` 사본이 안 따라와서 롤백이 안 됨 |
| 2 | 게인을 올렸음 | 게인은 적용됐고, 원인은 **기구 간섭**이었음 |
| 3 | 결합 로봇 검사 통과 (DOF·IK·AABB) | **재생하면 날아가고 넘어짐** |

**공통점: 검사가 전부 정적이었다.** 상태를 읽기만 하고 **시간을 돌리지 않았다.**

```
정적 검사는 "구조가 맞는가" 를 본다
동적 검사는 "동작하는가" 를 본다
후자를 안 하면 전자가 통과한 채로 실패한다
```

그래서 **재생 후 측정하는 시험 도구**(`settle_test_carter.py`)를 따로 만들었다. 이게 대응의 핵심이다.

## 2. 로봇팔 제어 — 겪은 것들

### 2-1. 책이 기울어진 채 서가로 갔다

| | |
| --- | --- |
| **증상** | 파지까지는 되는데 꽂을 때 책이 비스듬히 들어감 |
| **처음 의심** | 삽입 경로가 잘못됐나 |
| **실제 원인** | 에셋 자체가 **엉뚱한 축으로 누워 있었다.** 파지 순간의 기울기가 그대로 서가까지 따라간 것 |
| **봤어야 할 것** | 책을 잡기 전에 **에셋의 원래 자세**를 확인 |

**조치**: 24가지 회전을 시도해 세우는 자세를 찾고(`upright_quat()`), 서가에 붙이는 순간 다시 세운다.

### 2-2. 얇은 책이 트레이에서 쓰러졌다

| | |
| --- | --- |
| **증상** | 두꺼운 책은 되는데 얇은 책만 실패 |
| **실제 원인** | 충돌 근사가 실제 모양을 못 따라가 얇은 책이 넘어짐 |

**조치**: 충돌을 상자로 근사(`boundingCube`)해 세워 둔다.

### 2-3. 트레이 칸막이를 세웠더니 파지가 막혔다

`[이미지 2]` — 칸 간격 0.075 m 에 손가락이 들어갈 자리가 없는 그림

| | |
| --- | --- |
| **증상** | 칸막이를 넣자 "down 단계 시간 초과" |
| **실제 원인** | **칸 간격 0.075 m 안에 손가락이 지나갈 폭이 남지 않는다** |

**조치**: 칸막이를 없애고 책 충돌을 상자로 근사. **"현실적으로 보이게" 만든 것이 기능을 막은 사례.**

### 2-4. 같은 시험인데 M411 이 계속 나왔다

| | |
| --- | --- |
| **증상** | 노드를 새로 띄워도 목표가 계속 거절됨 |
| **처음 의심** | 노드 코드 문제 |
| **실제 원인** | **`ros2 daemon` 이 죽은 노드의 액션 서버 정보를 들고 있었다.** 노드를 새로 띄우는 것만으로는 안 풀린다 |
| **봤어야 할 것** | `ros2 action info /place_book` → **Action servers 개수** |

**조치**: `ros2 daemon stop`. 그리고 게이트 절차에 "서버가 1개인지" 를 넣었다.
**서버가 2개면 결과가 뒤섞인다** — 실제로 1 ms 만에 실패로 돌아오는 가짜 실패를 겪었다.

## 3. 로봇 교체(Nova Carter + M0609) — 가장 많이 배운 구간

### 3-1. 팔이 카터 위에 떠 있었다

`[이미지 3]` — 떠 있는 옆면 / `[이미지 4]` — 고친 뒤 옆면 (비교용)

| | |
| --- | --- |
| **증상** | 결합 로봇을 열면 팔이 공중에 떠 있음 |
| **처음 의심** | 장착 높이 계산 실수 |
| **실제 원인** | 카터 AABB 윗면(0.554)을 "상판" 으로 잡았는데 그건 **3D 라이다 꼭대기**였다. 장착점 바로 아래는 상판이 아니라 **또 다른 라이다** |
| **봤어야 할 것** | AABB 가 아니라 **실제 표면 높이** (광선을 쏴서 잼) |

`[이미지 5]` — 격자 광선으로 만든 **상판 높이 지도** (숫자 표)

더 큰 발견: **카터 상판에 평평한 20 cm 자리가 아예 없다.**
내리면 라이다를 깔고 앉고, 뒤로 옮기면 3D 라이다와 겹친다.
→ 실제로도 **어댑터 판 없이는 못 얹는 구조**였다.

### 3-2. joint_1 이 안 돌았다 — 게인 문제가 아니었다

| | |
| --- | --- |
| **증상** | 어깨·팔꿈치는 되는데 베이스 회전만 0.017 rad 밖에 안 움직임 |
| **처음 의심** | 게인이 낮다 |
| **확인** | 게인을 설정하고 **되읽어 보니 값이 들어가 있었다** |
| **실제 원인** | **장착 위치가 3D 라이다와 겹쳐 기구적으로 막혀 있었다** |

**[핵심] "게인을 올려도 안 된다" 는 게인 문제가 아니었다.**
게인이 적용됐음을 **확인했기 때문에** 다른 원인을 찾을 수 있었다.
→ 의심 항목을 **배제**하는 것이 원인 추적의 절반이다.

### 3-3. 재생하면 넘어지고, 스케일을 키우면 날아갔다

`[이미지 6]` — 조인트 로컬 좌표: 프레임 원점 vs AABB 중심 (39 cm 차이 그림)

원인이 **두 개**였고 둘 다 정적 검사로는 안 잡혔다.

| 원인 | 내용 |
| --- | --- |
| ① 고정 조인트가 **39.2 cm 어긋남** | 조인트 로컬 좌표는 **바디의 프레임 원점** 기준인데 **AABB 중심**으로 계산했다. 재생 순간 물리가 팔을 39 cm 끌어당겨 로봇이 튕겨 나갔다. 스케일을 키우면 그 힘이 커져 더 멀리 난다 |
| ② 드라이브 목표가 **85° 어긋남** | URDF 임포트가 `joint_3`·`joint_5` 목표를 90° 로 써 뒀는데 시작 자세는 0°. 강성 1e7 이 팔을 확 끌어당겨 로봇을 넘어뜨렸다 |

**측정 결과 (4초 재생)**

| 항목 | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| 기울기 | **91.8°** (옆으로 누움) | **0.15°** |
| 팔–베이스 어긋남 | **235 mm** | **1.4 mm** |

**곁가지 교훈**: 처음엔 반대 방향으로 고치려 했다 — 시작 자세를 90° 로 바꾸는 방법(`JointStateAPI`).
그랬더니 **로봇 전체가 90° 누워 버렸다.** 되돌리고 반대로 목표를 0° 에 맞췄다.
`[이미지 7]` — 잘못 고쳤을 때 로봇이 누운 그림

## 4. 비전 노드 결합 — 이틀을 쓴 문제

`[이미지 9]` — 증상이 층층이 가려져 있던 구조 (양파 그림)

### 증상

검출 요청을 보내면 **아무 반응이 없다.** 6회 시도에서 빈 칸 판정을 **한 번도 못 봤다.**

### 겉으로 보인 것 → 실제

| 단계 | 그때 보인 것 | 파고든 결과 |
| --- | --- | --- |
| 1 | "TF 변환이 실패한다" | 요청 시각이 TF 버퍼 밖 |
| 2 | "묵은 프레임을 쓴다" | 맞다. 최대 7.5초 묵음 |
| 3 | 최신 프레임을 쓰게 고쳤는데도 실패 | **트리거 → TF 조회까지 14.7초** 걸림 |
| 4 | 추론이 느린가? | **아니다. 0.13~0.15초** |
| 5 | 그럼 왜 한 번만 되고 마는가 | **요청이 한 번 실패하면 소모돼 사라진다** |
| 6 | 재시도하게 고쳤더니 판정까지 도달 | 그런데 **두 번째 요청부터 무반응** |
| 7 | 노드가 죽었나? | **아니다. 살아 있는데 CPU 91% 로 첫 처리에서 못 빠져나온다** |

**[핵심] "반응이 없다" 는 증상 하나가 최소 세 개의 다른 문제를 가리고 있었다.**

### 무엇이 결정적이었나

**진단 로그 두 줄.**

```
[진단] 동기 프레임 60개 수신, pending=False   ← 콜백이 사는지
[진단] 검출 요청 수신 data=True                ← 트리거가 오는지
```

이 두 줄로 "콜백이 죽은 것 / 요청이 안 온 것 / 처리가 안 끝난 것" 이 갈렸다.
**추측으로 반나절을 쓴 뒤, 계측 두 줄로 10분 만에 갈렸다.**

### 환경 차이가 만든 함정

이 PC 에는 **GPU 가 없다.** 그래서 첫 추론이 오래 걸리고 TF 버퍼를 벗어난다.
**비전 담당자 GPU PC 에서는 이 증상이 안 보일 수 있다.**
→ "내 PC 에서는 되는데요" 가 나올 수 있는 구조였고, 그래서 **측정값을 같이 넘겼다.**

### 남의 코드에 대한 개입 수위

우리 경로를 막고 있지 않았으므로 **진단까지만** 하고, 검증한 수정은 **우리 브랜치에만** 두고 문서로 넘겼다.
`[이미지 10]` — 개입 수위 판단 기준

```
내 작업이 막힌다     → 진단 + 수정 제안
내 작업이 안 막힌다  → 진단까지
```

## 7. 가장 뼈아픈 것 — **성공이라고 보고한 것이 성공이 아니었다**

`[이미지 11]` — 세 겹으로 가려져 있던 구조

사용자가 녹화본을 직접 보고 지적했다.

> 4권을 연달아 성공했다고 했는데 내가 직접 보니까 첫 권을 넣는 과정에서 책이 떨어졌는데
> 모든 책 성공이라고 했었어

확인해 보니 사실이었다. **2/4** 였다.

| 겹 | 무엇이 문제였나 |
| --- | --- |
| 1 | `verify()` 가 **"이번에 꽂을 책 하나"** 만 봤다. 다른 책이 떨어져도 안 보인다 |
| 2 | 그래서 `error_code: 0` 만 보고 **"4/4"** 라고 보고했다 |
| 3 | 장면 전체 검사를 넣었더니, 이번엔 **내 검사가 트레이의 정상 자세(책등 위)를 "쓰러짐" 으로 오판**했다 |

세 번째까지 고치고 나서야 진짜 실패가 드러났다 — **M406** 운반 중 손 안에서 3.1 cm 어긋남,
그리고 **M409** 로 책이 바닥에 떨어짐.

```
[원칙] 판정 기준이 좁으면, 도구가 맞고 검사를 돌려도 틀린 답이 나온다.
       "명령이 끝났다" 와 "결과물이 제자리에 있다" 는 다른 문장이다.
```

이건 앞의 두 교훈과 **층이 다르다.**

| 층 | 무엇이 틀렸나 | 사례 |
| --- | --- | --- |
| 1 | **검사 방법** — 정적으로만 봤다 | 결합 로봇이 재생하면 전복 |
| 2 | **검사 도구** — 도구가 틀린 답을 냈다 | 프레임 변환 누락으로 0/6 |
| 3 | **판정 기준** — 무엇을 통과로 볼지가 좁았다 | **여기** |

그리고 실패를 세는 방식 자체도 바뀌었다. 같은 구성에서 판마다 결과가 달라진다 —
**파지는 매번 같지 않다.** 책 두께가 제각각이라 손 안에서 미끄러진다.
그래서 "4/4 성공" 이 아니라 **"n 판 중 m 판"** 으로 말해야 한다.

## 8. 세계가 비어 있는 것은 검사에 안 걸린다 (2026-09-20)

§7 이 "무엇을 확인하느냐가 좁았다" 는 이야기였다면, 이 둘은 **같은 층의 다른 얼굴**이다.
도구도 맞고 계산도 맞는데, **검사가 묻는 질문이 좁았다.**

### 8-1. ENV-01 — 책이 안 꽂힌 게 아니라 **서가가 없었다**

M0609 로 바꾼 뒤 삽입이 매번 빗나갔다. 목표와 실제가 26 cm, 24 cm 차이났고
"좌표가 틀렸다" 고 보고 파라미터를 며칠 만졌다. 실제로는:

- 로봇은 월드 x ≈ **−5.77**, 서가는 x **−2.97 ~ +3.28**
- 팔은 계약 좌표까지 책을 **정확히** 옮긴 뒤 허공에 놓고 있었다. 책은 받침판으로 떨어졌다

검증 코드는 "목표점과 실제 위치가 얼마나 다른가" 만 봤다. 그래서 이것을 **좌표 오차**로 보고했다.

> **교훈**: 검증이 "숫자가 얼마나 다른가" 만 보면 **세계가 비어 있는 것**을 못 잡는다.
> 목표점에 **받쳐 줄 것이 실제로 있는지**를 따로 물어야 한다.

### 8-2. ENV-02 — 서가 16개 중 **콜라이더는 1개**

`shelf_05` 앞으로 옮겨 꽂았더니 책이 서가를 **통과해 바닥까지** 떨어졌다
(x·y 는 맞고 z 만 1.03 m 낮음). 광선을 쏴 보고서야 알았다 —
`_05` 로 쏜 광선은 전부 바닥면(z 0)까지 갔다.

```
shelf_brown__book_shelf_01   콜라이더 1개   ← 이것만 물리적으로 존재
나머지 15개                   콜라이더 0개   ← 눈에만 보이는 장식
```

서가에 **뒤판도 없다** — 양쪽에서 쏜 광선이 둘 다 관통한다.

> **교훈**: 시각 에셋은 **물리적으로 존재한다는 보장이 없다.**
> "보이니까 있다" 는 시뮬레이터에서 특히 위험한 가정이다.

### 8-3. 진단 도구가 **세 번 연속** 틀린 답을 줬다 — 계산이 아니라 시야가 문제였다

"무엇이 팔을 막는가" 를 알아내려고 만든 진단이 세 번 다 "문제 없다" 고 답했다.
세 번 다 **계산은 정확했고, 정답이 시야 밖에 있었다.**

| 시도 | 답 | 왜 틀렸나 |
| --- | --- | --- |
| 1차 링크 AABB 겹침 | "겹치는 게 당연한 것뿐" | `compute_aabb` 가 Xform 의 **하위 트리를 늘 포함** → link_2 안에 그리퍼가 들어감 |
| 2차 `include_children=False` | **결과가 완전히 동일** | Xform 에서는 그 옵션이 안 먹는다 |
| 3차 PhysX overlap | "팔 주변에 책밖에 없다" | **받침판·AMR 몸체를 내가 필터로 제외** — 정작 의심해야 할 대상 |

필터를 풀고 나서야 받침판과 트레이가 어깨 옆에 있다는 게 보였다.

**공통 구조**: 세 번 다 틀리게 만든 것은 **계산하는 줄이 아니라 범위를 좁히는 줄**이었다
(`include_*`, 제외 필터, 마스크).

> **교훈 — ④ 음성 대조(negative control)**
> 기존 자기검증 삼종(① 왕복 자기일치 ② 오답 주입 ③ 0 가정 깨기)은 도구의 **계산**을 본다.
> ④ 는 도구의 **시야**를 본다. 도구를 돌리기 **전에** 한 줄을 적는다:
>
> ```
> 반드시 잡혀야 하는 것: ___________
> ```
>
> 오늘이면 "받침판은 팔 옆에 분명히 있다". 결과에 그게 없으면 **결과 전체를 버린다.**
>
> **적용 조건은 하나로 못 박는다** — *"없다" 는 답은 음성 대조 없이는 결론이 아니다.*
> "있다" 는 답은 그 자체가 증거지만(도구가 무언가를 봤다),
> "없다" 는 **진짜 없거나 / 못 보거나** 둘이다. 이 비대칭 때문에 ④ 는 음성 결과에만 의무다.
>
> **딸린 규칙**: 조건을 바꿨는데 결과가 *완전히* 같으면, 결론을 내기 전에
> **조건이 정말 바뀌었는지**부터 확인한다. 자연스러운 실험은 보통 조금이라도 달라진다.

### 8-4. 곁가지로 찾은 것 — 계약값의 4 mm

M0609 삽입 z 를 `선반판 + 책높이/2 - 베이스` 로 계산해 0.5056 을 썼다.
웹 클로드가 "두 로봇의 **선반판 위 띄움**이 3.3 mm 다르다" 고 짚어서 다시 보니,
Franka 계약값에는 코드의 **삽입 여유 4 mm** (`grip_z = floor_z + Lb/2 + 0.004`) 가
들어 있었다. 같은 식으로 맞추면 **0.5097** 이다 (Franka 는 0.2 mm 오차로 재현된다).

허용 오차가 8 mm 인 작업에서 4 mm 는 절반이다.

> **교훈**: 물려받은 계약 숫자는 **어떻게 나온 값인지**를 재현할 수 있어야 한다.
> 재현이 안 되면 그 안에 설명 안 되는 상수가 섞여 있다.
