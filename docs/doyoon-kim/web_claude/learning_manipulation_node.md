# 학습자료 — `manipulation_node` 는 무엇을 하는 노드인가

> 팀원 설명용. **시각화는 웹 클로드가 제작**하므로 여기에는 내용만 둔다.
> 그림으로 만들면 좋을 곳에 `[그림 N]` 표시를 달았다.

---

## 0. 한 줄 요약

**`manipulation_node` 는 "책 한 권을 서가 어느 칸에 꽂아라" 라는 요청을 받아, 성공/실패를 코드로 돌려주는 창구다.**

FSM(`task_manager_node`)은 로봇팔이 어떻게 움직이는지 전혀 모른다.
비전은 좌표만 준다. 그 사이에서 **"꽂는 일" 전체를 책임지는 것이 이 노드**다.

---

## 1. 왜 노드를 따로 두었나

`[그림 1]` — 세 노드가 각각 무엇을 알고 무엇을 모르는지 (경계 그림)

```
비전          "빈 칸이 여기 있다"        좌표만 안다
  ↓
FSM           "book_3 을 저기 꽂아라"    순서와 상태만 안다
  ↓
로봇팔 노드    ← 여기가 manipulation_node
  ↓
Isaac 실행기   실제로 관절을 움직인다
```

**경계를 이렇게 그은 이유 세 가지:**

| 이유 | 설명 |
| --- | --- |
| **로봇이 바뀌어도 계약은 안 바뀐다** | 실제로 Franka(7축) → M0609(6축) 로 바뀌는 중인데, FSM 은 코드를 한 줄도 안 고친다 |
| **실패를 한 곳에서 번역한다** | "IK 해가 없음", "책을 못 잡음" 같은 로봇 사정을 **FSM 이 이해할 수 있는 코드**로 바꾼다 |
| **시뮬과 실물을 바꿔 끼운다** | `executor:=sim` / `real` 로 아래만 교체한다 |

## 2. 인터페이스 — ROS 2 Action 을 쓴다

`[그림 2]` — Topic / Service / Action 의 차이. **"오래 걸리고 중간 보고가 필요하며 취소할 수 있어야 하는 일"** 이 Action

```
Action: /place_book
Type:   shelving_interfaces/action/PlaceBook
```

### Goal (요청)

| 필드 | 뜻 | 규칙 |
| --- | --- | --- |
| `job_id`, `book_id` | 어느 작업의 어느 책인지 | 비어 있으면 거절 |
| `target_slot.header.frame_id` | 좌표의 기준 | **반드시 `arm_base_link`** |
| `target_slot.pose.position` | **꽂힌 뒤 책의 AABB 중심** | 팔이 닿는 범위 안이어야 함 |
| `target_slot.pose.orientation` | 삽입 방향 | **yaw +90°** (책을 눕혀 끼운다) |

> **왜 "꽂힌 뒤의 위치" 인가**: "책을 어디에 놓을지" 를 손끝 위치로 주면 로봇이 바뀔 때마다 의미가 달라진다.
> **결과물의 최종 위치**로 정의하면 로봇과 무관해진다. `[그림 3]` — 손끝 기준 vs 결과물 기준

### Feedback (중간 보고)

지금 어느 단계인지 계속 보낸다 — `PLANNING_GRASP` → `APPROACH` → `GRASP` → `LIFT` → `INSERT` → `VERIFY`

`[그림 4]` — 단계별 팔 자세 6컷 (녹화 영상에서 뽑을 수 있다)

### Result (결과)

| 필드 | 뜻 |
| --- | --- |
| `error_code` | 0 이면 성공, 아니면 실패 원인 |
| `failed_phase` | **어느 단계에서 실패했는지** |
| `placement_verified` | 실제로 꽂혔는지 확인한 결과 |
| `message` | 사람이 읽을 설명 |

## 3. 핵심 설계 — 실패를 숫자로 말한다

`[그림 5]` — 오류 코드 표를 그림으로 (코드 / 뜻 / FSM 이 할 일)

| 코드 | 언제 | FSM 이 해야 할 일 |
| --- | --- | --- |
| **410** | 요청 자체가 잘못됨 (방향·범위·프레임·ID) | **재시도해도 소용없다.** 비전 좌표를 다시 받아야 한다 |
| **411** | 로봇팔이 아직 준비 안 됨 | 잠시 뒤 재시도 |
| **412** | 취소됨 | 정상 종료로 처리 |
| 404 / 405 / 407 / 409 | 파지·삽입 중 실패 | 다음 책으로 넘어가거나 재시도 |

**[중요] 410 과 411 을 나눈 이유**: 둘 다 "실패" 지만 **FSM 이 할 일이 정반대**다.
410 에 재시도를 걸면 영원히 같은 자리에서 돈다. **오류 코드는 원인 분류가 아니라 "다음에 무엇을 할지" 로 나눈다.**

### 실제 거절 메시지 (2026-09-19 실측)

| 잘못된 요청 | 돌아오는 메시지 |
| --- | --- |
| 방향이 yaw 0° | `삽입 방향 yaw 0.0° — 1차 지원 90°±6°` |
| 위치가 범위 밖 | `꽂을 위치 (0.55, 0.0, 0.8) 가 검증 범위 밖 [-0.56, 0.45, 0.25]~[-0.22, 0.65, 0.45]` |
| 프레임이 다름 | `TargetSlot frame_id 'map' ≠ 'arm_base_link'` |
| ID 누락 | `job_id 와 book_id 가 필요하다` |

> **메시지에 "무엇이 왜 틀렸고 무엇이어야 하는지" 를 다 넣는다.**
> 이렇게 해야 다른 담당자가 자기 코드를 스스로 고칠 수 있다. `[그림 6]` — 나쁜 메시지 vs 좋은 메시지 비교

## 4. 내부 구조 — 두 겹으로 나뉜다

`[그림 7]` — 노드 안쪽 2계층 구조

```
manipulation_node          ROS 창구. 요청 검사 · 상태 관리 · 오류 코드 번역
   └─ executor             실제 실행. sim / real 로 교체
        └─ (sim) Isaac 실행기와 토픽으로 대화
```

**핵심: 위층은 "무엇을" 알고, 아래층은 "어떻게" 를 안다.**

| 위층이 하는 일 | 아래층이 하는 일 |
| --- | --- |
| 요청이 규칙에 맞는지 검사 | IK 풀기 |
| 지금 다른 작업 중인지 관리 | 경로 만들기 |
| 실패를 코드로 번역 | 그리퍼 여닫기 |
| 취소 처리 | 꽂혔는지 확인 |

로봇이 M0609 로 바뀌면 **아래층만 바뀐다.** 실제로 그렇게 만들어 두었다
(`robot_profiles.py` 한 파일에서 관절 이름·프레임·그리퍼 방식을 고른다).

## 5. 동작 한 판 따라가기

`[그림 8]` — 시퀀스 다이어그램 (FSM → 노드 → Isaac → 노드 → FSM)

```
1. FSM 이 goal 을 보낸다           "book_0 을 (-0.3497, 0.5495, 0.3399) 에, yaw 90°"
2. 노드가 요청을 검사한다          프레임? 범위? 방향? ID?  ← 여기서 410 이 나온다
3. 파지 계획                      트레이에서 그 책을 찾고, 잡을 지점을 정한다
4. 접근 → 파지 → 들어올리기
5. 서가로 이동 → 삽입
6. 꽂혔는지 확인                  실제 책 위치를 재서 목표와 비교
7. 결과를 돌려준다                error_code 0, placement_verified true
```

**6번이 있는 이유**: "명령을 보냈다" 와 "실제로 꽂혔다" 는 다르다.
확인 단계가 없으면 **실패한 것을 성공으로 보고**하게 된다.

## 6. 실측 숫자 (2026-09-19, Franka 경로)

| 항목 | 값 |
| --- | --- |
| 4권 연속 | **2/4** (2026-09-20 재측정) |
| 권당 소요 | 22~25초 (녹화 없이) |
| 실패 내용 | **M406** 운반 중 손 안에서 책 3.1 cm 어긋남 / **M409** 책이 바닥으로 떨어짐 |
| 잘못된 요청 4종 | 전부 명확한 메시지와 함께 거절 |

> **[정정]** 이 표는 원래 "4/4 성공" 이었다. 그 숫자는 **`error_code` 만 보고** 낸 것이고,
> 검증 코드가 "이번에 꽂을 책 하나" 만 확인해서 **다른 책이 떨어져도 성공으로 보고**됐다.
> 장면 전체를 확인하도록 고친 뒤 다시 재니 2/4 였다. 자세한 경위는 시행착오 문서 §7 참조.
>
> **설명할 때 이 점을 같이 말하면 좋다** — 5절 6번("꽂혔는지 확인") 이 왜 있는지가
> 바로 이 사건이다. 확인 단계가 있어도 **무엇을 확인하느냐**가 좁으면 소용없다.

---

## 7. 팀원이 기억하면 좋은 것 세 가지

1. **좌표는 `arm_base_link` 기준, 책의 AABB 중심, yaw +90°.** 셋 중 하나만 틀려도 410 이다
2. **410 은 재시도 금지.** 요청을 고쳐야 한다
3. **로봇이 바뀌어도 이 계약은 안 바뀐다.** 그게 이 노드를 따로 둔 이유다
