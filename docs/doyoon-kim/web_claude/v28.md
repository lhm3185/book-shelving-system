## 1. v27 의 가설들은 **전부 틀렸다**. 실제 원인은 다른 데 있었다

v27 에서 가설 A~D 를 세웠는데, 하나씩 실측으로 확인한 결과 전부 기각됐다.

| v27 가설 | 판정 | 기각 근거 |
| --- | --- | --- |
| A. `XFormPrim.set_world_pose` 가 xform 스택을 갈아엎어 스케일 손실 | **기각** | 트레이는 이미 `translate/orient/scale` 로 저장돼 있었다. `SingleXFormPrim` 생성 전후 월드 AABB 변화 **0.00000 m** |
| B. `convexDecomposition` 파라미터가 부족해 칸이 메워진다 | **기각** | `sdf`(해상도 512)로 바꿔도 **결과가 완전히 동일**했다 (책 바닥 0.415 → 0.413) |
| C. 동적 강체를 좌표로 끌어 물리와 싸운다 | **부분 참** | 이송 방식 문제는 맞았다 (§2-4) |
| D. 책 초기 배치가 칸 위가 아니다 | **기각** | 책 5권의 x 가 칸 중심에서 **전부 1.3 cm 이내**. 칸 폭 6.5~8.2 cm, 책 두께 3.4~4.4 cm |

**가설 A 는 사실 확인이 절반은 맞았다.** Isaac 5.1 의 `xform_prim.py:1194 _set_xform_properties()` 는 실제로
`properties_to_remove` 에 `xformOp:transform` 을 넣어 **지우고**, `xformOp:scale` 이 없으면 **(1,1,1)로 만든다.**
복원하는 것은 위치·회전뿐이라 **행렬에 스케일이 들어 있던 프랍은 스케일을 잃는다.**
이번 트레이가 그 형태가 아니었을 뿐이므로, 행렬로 저장된 다른 프랍에는 여전히 위험하다.

## 2. 진짜 원인 ① — 내 코드가 레벨 트레이의 콜리전을 매 실행 지우고 있었다

**이것이 "콜리전이 수정 전 상태다" 의 정체다.** 사용자는 처음부터 이렇게 말했고, 나는
USD **파일**을 읽어 `convexDecomposition` 이 적혀 있는 것을 확인하고 "정상"이라고 반박했다.
파일은 맞았다. **코드가 런타임에 덮어쓰고 있었다.**

`book_scene.py:370` (수정 전):

```python
for p in Usd.PrimRange(st.GetPrimAtPath(self.tray)):
    if p.IsA(UsdGeom.Mesh) and _tray_coll:
        UsdPhysics.CollisionAPI.Apply(p)
        UsdPhysics.MeshCollisionAPI.Apply(p).CreateApproximationAttr().Set("none")   # ←
```

예전에 스폰하던 `bs_tray` 는 **정적 콜라이더**(RigidBodyAPI 없음)라 `none`(삼각망)이 맞았다.
그런데 레벨의 트레이는 **동적 강체**다. 동적 강체에 삼각망은 불법이라 PhysX 가 조용히 대체한다:

```
PhysicsUSD: Parse collision - triangle mesh collision (approximation None/MeshSimplification)
cannot be a part of a dynamic body, falling back to convexHull approximation:
/World/tray_books/tray_v3/tray_mt_02/Cube_003.
```

**볼록 껍질 = 칸이 메워진 덩어리.** 그래서 책이 칸에 안 들어가고 그 위에 얹혔다:

```
트레이 칸 바닥 z = 0.3200
책 바닥 z        = 0.4151 … 0.4157   (5권 전부, 5초 뒤에도 그대로)
```

**`sdf` 로 바꿔도 같았던 이유도 이것이다** — 내가 `sdf` 로 설정한 **뒤에** 이 코드가 다시 `none` 으로 덮었다.
즉 A/B 시험 자체가 무의미했다. 시험을 설계할 때 **내 코드가 그 값을 만지는지** 먼저 봤어야 했다.

**고침**: 레벨 트레이를 쓸 때는 콜리전에 손대지 않는다 (`and not self.use_level_tray`).
폴백 경고가 **0건**이 되었고, 새 트레이에서 책 바닥이 0.347(트레이 안쪽 바닥)에 제대로 앉는다.

### 이것을 잡아내는 지표 (v27 회신 §9 M3 이 정확했다)

```bash
grep -c "falling back to convexHull" isaac.log    # 0 이 아니면 콜리전이 내 생각과 다르다
```

한 줄이면 됐다. 며칠을 쓴 문제였다.

## 3. 진짜 원인 ② — 트레이 경로 하드코딩 → 조용한 스폰 대체

`KIOSK_TRAY` 기본값이 `/World/tray_books/tray_v1` 로 **하드코딩**돼 있었다.
레벨에는 `tray_v3` 가 들어 있었으므로, 환경변수를 주지 않고 실행하면:

1. `tray_v1` 을 못 찾는다
2. `use_level_tray = False` 가 된다
3. **아무 말 없이** 옛 에셋(`tray_v1.usdc`)과 책 5권을 스폰한다
4. 화면에는 스케일도 콜리전도 다른 트레이가 나온다. **로그는 멀쩡하다**

v27 회신의 §0/§1 이 지적한 구조가 바로 이것이다. 다만 회신은 푸시본 `8137701` 을 본 것이라
"레벨 트레이를 `SetActive(False)` 로 끈다" 까지 갔는데, 로컬에는 그 뒤 `use_level_tray` 분기가
들어가 있어서 **내가 환경변수를 준 실행에서는** 그 경로를 비껴가고 있었다.
**기본 실행 경로에서는 회신의 지적이 그대로 맞았다.**

**고침 두 가지:**

- 기본값을 레벨과 맞추고, **이름이 안 맞으면 폴더에서 찾는다.** 후보가 여럿이면 예외로 멈춘다
- `SIM_USE_LEVEL_TRAY` 가 켜져 있는데 못 찾으면 **즉시 예외.** 조용한 대체 금지

에셋이 `tray_v3` → `tray_04` 로 바뀌었을 때 실제로 이렇게 동작했다:

```
**트레이를 이름으로 못 찾아 폴더에서 찾았다**: /World/tray_books/tray_04
  (원래 찾던 경로 /World/tray_books/tray_v3 가 레벨에 없다)
```

예전 같았으면 여기서 조용히 옛 에셋을 스폰했을 자리다.

## 4. 진짜 원인 ③ — 이송을 "동적 강체 + 속도" 로 밀었다

v27 §5 의 시도들이 왜 실패했는지가 실측으로 갈렸다.

| 방식 | 결과 |
| --- | --- |
| 정적 콜라이더를 `set_world_pose` | 속도가 0 이라 마찰이 없다 → **트레이만 가고 책은 남는다** |
| 동적 강체 + `set_linear_velocity` | 반납기 위 마찰이 매 스텝 상쇄 → **82.5 cm 중 6.4 cm** 만 가고 멈춤. 막힌 동안 `(목표−현재)/dt` 가 눈덩이처럼 커져, 접촉이 풀리는 순간 **책이 날아갔다** |
| **키네마틱 + 구간 목표 → 도착 후 동적 복귀** | ✅ **성공.** 책이 하나도 안 흔들리고 실려 온다 |

v27 회신 §2 의 표와 §3-1 의 권고가 정확했다. 키네마틱은 물리가 밀지 못해 속도가 커질 수 없고,
(목표−현재)/dt 가 곧 속도라 접촉·마찰이 생긴다.

**추가로 발견한 것 — 회신 §3-1 의 "데크 2 mm 위" 항목이 실제로 필요했다.**
키네마틱 트레이가 데크에 닿은 채 움직이자 **동적인 로봇이 −x 로 밀려났다.**
이송 중 4 mm 띄우고, 멈춘 뒤 동적으로 되돌려 내려앉히니 로봇이 움직이지 않는다.

```python
_r = min(1.0, s / 0.05)                      # 처음 5% 에 걸쳐 부드럽게 들어올린다
want[2] += TRAY_CLEAR_M * (_r * _r * (3.0 - 2.0 * _r))
```

## 5. 진짜 원인 ④~⑥ — 타이밍, 팔 자세, 회전 없음

### ④ 이송이 끝나기 전에 로봇이 출발했다

녹화를 켜면 시뮬 시간이 실제보다 느려져서 "15초 기다렸으니 됐겠지" 가 틀렸다 (시뮬로는 8초).
그 결과:

```
이송 끝(480스텝)  트레이 (4.993, −5.659)  앵커 (4.986, −5.607)   차이 (+0.007, −0.052)
540스텝           트레이 (4.581, −5.224)  앵커 (4.436, −5.026)   차이 (+0.145, −0.198)  ← 20 cm 튐
이후 계속          차이 (+0.145, −0.198) 로 **고정**
```

이송이 끝나는 순간 `rebase_tray_to` 가 **그때의 앵커**로 상대 위치를 기록하는데,
로봇이 이미 움직이고 있어서 **어긋난 20 cm 가 영구히 박혔다.** 트레이가 데크 모서리에 걸린 채 주행했다.

**고침 둘:** 이송 중에는 주행을 **상태로** 막는다(시간으로 재지 않는다). 그리고 rebase 는
기록해 둔 목표값이 아니라 **지금 실제 트레이 자세**를 읽어 같은 순간의 값끼리 쓴다.

### ⑤ `--start-home keep` 가 비전을 막고 있었다

카메라는 손목에 달려 있다. 레벨의 팔 자세를 그대로 두니 **카메라가 엉뚱한 데를 봤다.**
`/rgb` 는 11.2 Hz 로 멀쩡히 나오고 있었는데도 비전이 좌표를 못 냈다.
(중간에 "센서 게이트가 안 열린 탓" 이라고 단정했다가 토픽 발행률을 재서 **스스로 기각**했다.
토픽은 나오고 있었다.)

`--start-home move` 로 되돌리자 바로 검출됐다.

### ⑥ 주행이 방향을 바꾸지 않았다

`navigation_executor` 에 `# yaw 는 건드리지 않는다 (1단계)` 라고 적힌 채 **평행이동만** 했다.
그래서 책장 앞에 가도 로봇이 서가를 등지고 있었다.

**필요한 yaw 를 계산으로 구했다** (추측하지 않았다):

```
로봇 루트 yaw      90.00°   (레벨 시작)
팔 +Y 축 방향     −180.00°  ← 서가 반대편
서가 앞면 법선     ±Y       (y 로 얇다: 1.412 × 0.305, 중심 (2.572, −2.422))
파지 자리          (2.535, −3.019) — 서가 앞 0.598 m
```

팔 +Y = 루트 yaw + 90° 이고 서가 앞면을 정면으로 보려면 팔 +Y = +90° → **루트 yaw = 0°**.
도착 후 3초에 걸쳐 smoothstep 으로 돌린다. 실측 **+0.00°**.

## 6. 남은 것 — 401 손목 특이점 (질문은 이것 하나)

```
작업 vision_47 FAILED {'error_code': 401,
  'message': '계획 실패 approach: 32배까지 잘게 나눠도 한 걸음이 1.571 rad 이다 (손목 특이점으로 본다)'}
```

- `1.571 rad` = 정확히 **π/2**. 접근 경로 중간에 손목 관절이 90° 뒤집힌다 (IK 가지 전환)
- **잘게 나누기로는 안 풀린다.** 32배로 나눠도 그 계단이 그대로 남는다 — 경로가 아니라 **해 선택**의 문제다
- 비전이 준 목표 자체는 정상이다: 파지 (−0.3633, +0.0077, +0.1952), 삽입 (−0.3497, +0.5495, +0.3399)

**내가 생각하는 방향**: 스캔 자세 계획에서 같은 문제를 이미 겪었고 다중 씨앗으로 풀었다.
`scan_planner.seeds_for()` 는 앞 자세·홈에 더해 joint 1·3·5·7 을 ±0.6/±1.2 rad 흔든 변형까지
IK 로 풀어 **앞 자세와 가장 가까운 해**를 고른다. 이웃 자세 사이 최대 관절 변화가
254.6° → 83.3° 로 줄었다. 파지 접근 경로에도 같은 방식을 쓰면 될 것 같다.

## 7. 이번에 얻은 교훈 (다음에 같은 실수를 피하려고 적는다)

1. **파일에 적힌 값과 런타임 값은 다르다.** USD 를 읽어 "정상" 이라고 판단했지만 코드가
   런타임에 덮어쓰고 있었다. 설정을 확인할 때는 **내 코드가 그 값을 만지는지 먼저 grep** 해야 한다.
2. **조용한 대체(silent fallback)가 가장 비싸다.** 못 찾으면 멈춰야 한다. 대신 옛 것을 쓰면
   화면은 틀리고 로그는 맞아서 원인을 엉뚱한 데서 찾게 된다. 이번 사태의 절반이 이것이었다.
3. **명령값을 로그에 찍으면 안 된다.** `[이송] 트레이 안착 [4.993, …]` 은 목표값이었다.
   트레이가 6.4 cm 만 가고 멈춘 실행도 똑같이 초록불이었다. 지금은 실측값과 오차를 찍는다.
4. **시간으로 기다리지 말고 상태로 기다린다.** 녹화를 켜면 시뮬 시간이 달라져 "몇 초 기다림" 이 깨진다.
5. **사용자가 화면으로 본 것이 사실이다.** 내 로그가 초록이어도 그렇다. 어긋나면 내 계측을 의심해야 한다.
6. **같은 도메인에 시뮬이 여러 개 뜨면 안 된다.** 중단된 실행이 쌓여 Isaac 이 3개 떠 있었고,
   `/clock` 과 TF 발행자가 겹쳐 비전이 엉뚱한 시뮬을 보고 있었다. 실행 전에 항상 정리한다.
7. **정리 스크립트에 자기 이름을 넣지 말 것.** `pgrep -f` 패턴에 실행 스크립트 이름을 넣어
   스스로를 죽였다. (이전에는 대화형 셸을 4번 죽였다.)

| `SIM_KIOSK_TRAY` | `/World/tray_books/tray_v3` | 없으면 폴더에서 자동 탐색 |
| `SIM_TRAY_SETTLE_S` | 2.0 | 책이 칸에 앉기를 기다리는 시간 |
| `SIM_TRAY_DELIVERY_S` | 2.5 | 이송 시간 (현재 6.0 으로 실행) |
| `SIM_TRAY_CLEAR` | 0.004 | 이송 중 데크에서 띄울 높이 |
| `SIM_TRAY_CARRY` | 1 | 주행 중 트레이를 좌표로 끈다. Nav2(바퀴 구동) 들어오면 0 으로 |
| `SIM_TURN_S` | 3.0 | 도착 회전 시간 |
| `SIM_HANDS_OFF` | 0 | 1이면 트레이·책에 아무것도 안 한다 (기준선 확인용) |

**주행 중 트레이가 따라오는 것은 물리가 아니라 좌표다.** 루트를 `set_world_pose` 로
순간이동시키는 현재 주행 방식에서는 마찰이 생길 수 없다. 팀원의 Nav2(`cmd_vel` → 바퀴)가
들어오면 `SIM_TRAY_CARRY=0` 으로 바꿔 진짜 마찰로 실려 가게 할 수 있다. 스위치는 만들어 뒀다.
