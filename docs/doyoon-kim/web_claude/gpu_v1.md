## 0. 소통 규칙 (2026-09-17 합의)

| 항목 | 규칙 |
| --- | --- |
| 메인 PC → GPU PC | 기존 `sync_to_gpu.sh` (10분 주기, 단방향) |
| GPU PC → 메인 PC | GPU PC가 **scp로 메인 PC의 `docs/web_claude/`에 직접 올린다.** 동기화로 GPU PC에도 돌아온다 |
| 파일명 | **`gpu_vN.md`** — 메인 PC의 `vN.md`와 번호가 겹치지 않게 한다 |
| 정정 | **기존 문서를 고치지 않고 버전을 올려 쌓는다** |

### 동기화 스크립트 동작 (확인한 사실)

- `docs/`는 `rsync --delete`로 동기화된다 → **GPU PC가 `docs/` 안에 직접 쓴 파일은 10분 안에 지워지거나 덮어써진다.** v2 소실 원인
- 최상위 `*.py *.json *.sh *.yaml`도 메인 PC 판으로 덮어써진다(삭제는 안 함). **GPU PC에서 스크립트를 고치면 메인 PC에도 반영해야 유지된다**
- 데이터·`runs/`·`usd_v2/`는 동기화 대상이 아니다
- GPU PC 원본 보관: `~/gpu_reports/` (동기화 대상 아님)

## 3. YOLO 학습 결과 (3-4)

| 항목 | 값 |
| --- | --- |
| 모델 | YOLO11n-seg, 100에폭, batch 16, imgsz 640 |
| 데이터 | `yolo_seg_all` — train 3,510 / valid 345 / test 345 (여러 권: 360 / 45 / 45) |
| 학습 시간 | 27.5분 (에폭당 약 16초) |
| 가중치 | `runs/segment/runs/book/weights/best.pt` |

### 평가 집단별 수치

| 평가 집단 | 학습 포함 여부 | Box mAP50 | Box mAP50-95 | Recall | Mask mAP50 | Mask mAP50-95 |
| --- | --- | --- | --- | --- | --- | --- |
| 전체 valid 345장 | 미포함 | 0.994 | 0.978 | 0.985 | 0.992 | 0.963 |
| test 한 권짜리 300장 | 미포함 | 0.995 | 0.995 | 1.000 | 0.995 | 0.995 |
| 겹침 450장 (메인 PC 측정) | **포함** | 0.957 | 0.898 | 0.895 | 0.934 | 0.846 |
| **test 겹침 45장 (GPU PC 측정)** | **미포함** | **0.896** | **0.792** | **0.763** | **0.853** | **0.722** |

**CP1 성능을 보고할 때는 마지막 줄을 함께 써야 한다.** 겹침 450장 수치는 학습에 쓴 이미지를 포함하므로 낙관적이다.
단, 45장은 표본이 작고, 장면 단위 분할이라 **책 자체는 train에 있다**(새 책에 대한 일반화는 측정되지 않았다).

## 4. 문서와 다르게 진행한 것

| 항목 | 문서 | 실제 | 이유 |
| --- | --- | --- | --- |
| 장수 지정 | `--views 150` | config 사본의 `views`를 150으로 수정 | `build_datasets.py`는 **config 항목의 `views`가 명령줄보다 우선**한다. 그대로면 40장 |
| 두 번째 일괄 생성 | seed 기본값 | `--seed 100` | 두 실행 모두 seed 0부터 시작해 카메라·조명 시퀀스가 겹친다 |
| 학습 데이터 | `yolo_seg`만 | 한 권짜리 + 여러 권 합침 | CP1 상황을 학습·검증에 포함 |
| 여러 권 분할 | `export_yolo.py` 책 단위 분할 | **장면 단위 80/10/10** | 여러 권은 에셋 하나가 "책 1개"로 묶여 450장이 전부 train으로 갔다 → 검증 불가 |
| 결과 경로 | `runs/segment/book/` | `runs/segment/runs/book/` | ultralytics가 경로를 한 단계 중첩 |

**`build_datasets.py`의 views 우선순위와 `export_yolo.py`의 여러 권 분할은 메인 PC 스크립트에서 수정할 가치가 있다.**

## 5. `check_labels.py`의 `CHECK`는 원점 위치 때문이다

소규모 생성 65장 중 14장이 `CHECK`였다. 메인 PC 840장에서도 같은 에셋에서 같은 비율로 나온다
(`C_book002_low` 38/40, `C_book003_low` 32/40, 백과사전 권당 7~17/40). GPU 환경 문제가 아니다.

| 에셋 | 로컬 박스 중심 (원점 기준) |
| --- | --- |
| `C_book002_low` (FBX) | [92.2, 0, 0] — 원점이 책 밖 |
| `book_encyclopedia_set_01_book02` | [0, 0.082, 0.119] — 원점이 바닥면 |
| `book_softcover_01_cover01` | [0, 0, 0.113] — 원점이 바닥면 |

검사가 "라벨 거리(원점) ≈ 책 중심"을 가정하므로 원점이 치우친 에셋에서 틀린 경고가 난다.
**2D 라벨(투영·bbox·마스크)에는 영향이 없다.**

**판단 필요**: 라벨 `translation`/`T_cam_obj`는 **원점 기준**이다. 파지점으로 직접 쓰는 코드가 있다면
bbox 중심 기준으로 보정해야 한다. (`estimate_pose.py`는 크기 기반으로 비교하므로 해당 없음)
