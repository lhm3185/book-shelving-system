# 2026-09-21 시행착오 기록 — 다섯 건

형식: **증상 → 처음 의심한 것 → 실제 원인 → 봤어야 할 것**

낮에 밟은 함정을 그대로 적는다. 셋은 "환경이 바뀌어서", 둘은 "내가 만든 문제를
남의 탓으로 본 것" 이다. 뒤의 둘이 더 비쌌다.

---

## 1. 같은 PC 안에서 노드끼리 서로를 못 찾는다

| | |
| --- | --- |
| **증상** | GPU PC 에서 Isaac 은 멀쩡히 돌고, **노트북에서는 토픽이 다 보이는데**, 정작 그 PC 안에서 `ros2 topic list` 하면 `/parameter_events`, `/rosout` 뿐 |
| **처음 의심** | 도메인 ID 불일치. 다음으로 Isaac 이 ROS 브리지를 못 올린 것 |
| **실제 원인** | `~/.ros/fastdds_whitelist.xml` 이 UDPv4 를 특정 랜카드로 묶고 `useBuiltinTransports=false` 로 **공유메모리·로컬호스트 전송을 꺼버린다.** 다른 PC 와는 되는데 **같은 PC 안**이 막힌다 |
| **봤어야 할 것** | "밖에서는 되는데 안에서는 안 된다" 는 방향이 이미 답이었다. **전송 계층**을 의심했어야 했다 — 디스커버리는 도메인만의 문제가 아니다 |

> 덫 안의 덫: `unset FASTRTPS_DEFAULT_PROFILES_FILE` 로는 안 꺼진다. 스크립트가
> `${VAR:-기본값}` 으로 도로 켠다. 빈 문자열도 안 된다 (`realpath failed` 후 또 기본값).
> **있지만 아무 것도 안 하는 파일**(`config/fastdds_local.xml`)을 가리켜야 한다.

## 2. vision_manager 가 조용히 죽는다

| | |
| --- | --- |
| **증상** | "비전 좌표가 20초 안에 오지 않았다". 노트북에서는 멀쩡하던 코드가 GPU PC 에서만 |
| **처음 의심** | 모델 파일 경로, 도메인, 카메라 토픽 |
| **실제 원인** | **cv_bridge 가 그 PC 에서 못 쓴다.** OpenCV 5 가 `CV_CN_SHIFT` 를 3→5 로 바꿔 `CV_8UC3` 가 16 이 아니라 64 → `cv2_to_imgmsg` 가 `KeyError`. 그리고 컴파일된 `cvtColor2` 가 NumPy 1.x 빌드라 NumPy 2.x 에서 **세그폴트** |
| **봤어야 할 것** | "PC 를 옮겼더니 안 된다" 면 **판 번호를 먼저 찍어본다.** 파이썬 예외가 아니라 프로세스가 통째로 사라졌다는 점도 단서였다 — 순수 파이썬 코드는 그렇게 안 죽는다 |

## 3. 화면 그리기가 본선을 끊었다

| | |
| --- | --- |
| **증상** | 첫 파지는 되는데 그 다음 검출부터 좌표가 안 온다 |
| **처음 의심** | 검출 실패, 트리거 토픽 |
| **실제 원인** | 디버그 영상 오버레이에서 `KeyError: 'row_index'` → **노드 전체가 내려갔다.** 빈 칸 정보 구성이 경로마다 달랐다 |
| **봤어야 할 것** | 곁가지(화면)가 본선(검출·좌표 발행)을 끊을 수 있는 구조였다. **부수적인 것은 예외를 삼켜야 한다** |

## 4. 주행 뒤 삽입이 깨진다 — 내가 만든 문제 ①

| | |
| --- | --- |
| **증상** | 주행 없이는 `verified=True`. 한 바퀴 돌면 배치 검증 5항목이 **전부 false** (= 책이 바닥) |
| **처음 의심** | 주행 복귀 오차. 도착 허용 오차 5 cm 에서 그냥 멈추는 것 |
| **실제 원인** | 복귀 오차를 0 으로 만들어도 그대로였다. **루트 XForm 은 웨이포인트에 정확히 서는데 팔 베이스(관절로 매달린 몸체)가 8.1 cm·4.37° 처진다.** 파지·삽입 좌표가 전부 팔 기준이라 그 처짐이 그대로 오차였다 |
| **봤어야 할 것** | **"복귀 오차 0" 은 루트를 잰 값이었다.** 팔이 신경 쓰는 것은 팔 베이스다. 판정 지표가 틀리면 맞는 숫자가 틀린 결론을 낸다 |

> 진단 규칙 하나를 얻었다: 책들이 **월드에서는 y 가 전부 같은데 팔 기준 y 만 칸마다
> 벌어지면** 책이 흐트러진 게 아니라 **좌표계가 돌아간 것**이다.

## 5. 406 운반 중 미끄러짐 — 내가 만든 문제 ②

| | |
| --- | --- |
| **증상** | 4번을 고치자 실패가 409 → 406 "운반 중 손 안에서 책 3.1 cm 어긋남" 으로 옮겨갔다 |
| **처음 의심** | 기존 M406 가설(손가락 지령과 고정 조인트가 싸운다). "주행 뒤에만 난다" 는 새 사실을 그 위에 얹으려 했다 |
| **실제 원인** | **내 복귀 보정이 트레이를 끌고 갔다.** 보정은 루트를 옮겨 팔 베이스를 맞추는데 트레이 앵커(차체)도 함께 끌려가, 추종이 트레이를 따라 옮기면서 칸 중심에 **정확히 있던** 책이 5.4 cm 밀렸다 |
| **봤어야 할 것** | 추적 로그를 **보정 앞뒤로** 찍자마자 드러났다. `보정전` 에는 책이 칸 중심에 0.2 mm 오차로 있었다. **고치기 전에 앞뒤를 찍었어야 했다** — 나는 증상만 보고 세 번 고쳤다 |

### 여기서 파생된 잘못된 결론 하나

틀어진 좌표계에서 읽은 값으로 **"설정 칸 y 가 실제와 1.3~2.4 cm 어긋난다"** 고 판단해
y 보정을 뺐다. 기울기를 걷어내 보니 칸별 퍼짐이 **정확히 0** 이었다 — 칸마다 어긋난 게
아니라 **좌표계가 4.36° 돌아간 것 하나**였고, 그 값은 복귀 보정이 잰 4.37° 와 같았다.

> **틀어진 기준으로 잰 값으로 설정값을 부정하지 말 것.** 기준부터 세우고 다시 잰다.

## 얻은 지표 두 가지

| 지표 | 정상 | 이상 |
| --- | --- | --- |
| **파지 x 스냅 크기** (`칸 중심에 맞췄다: … N mm`) | ~0.3 mm | 10 mm 이상 → 트레이가 설정 자리에서 벗어남 |
| 책들의 **팔 기준 y 퍼짐** | 0 | 칸마다 벌어짐 → 좌표계가 돌아감 |

둘 다 **파지하기 전에** 이상을 알려준다. 실패한 뒤 원인을 캐는 것보다 훨씬 싸다.

## 부수 함정

- **`pkill -f <패턴>` 을 명령줄에 직접 쓰면 자기 명령줄이 걸려 셸까지 죽는다.**
  패턴은 스크립트 파일 안에 두고 PID 로 죽인다 (하루에 세 번 밟았다).
- Isaac 은 `python.sh` 가 kit python 을 또 띄운다. **부모만 죽이면 자식이 고아로 남아**
  다음 실행과 토픽이 충돌한다 → `setsid` 로 띄우고 **프로세스 그룹째**(`kill -TERM -PID`).
- `rqt_image_view` 는 TERM 을 무시한다. KILL 이 필요하다.
- bash 에서 `"${ARR[@]:-}"` 는 빈 배열을 **빈 문자열 하나**로 펼친다 →
  `unrecognized arguments: `. bash 4.4+ 는 `"${ARR[@]}"` 가 이미 안전하다.
